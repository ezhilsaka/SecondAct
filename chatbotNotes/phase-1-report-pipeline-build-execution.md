## 5) Major Architecture Decisions Locked During Execution

### Platform and infrastructure

- database: Supabase Postgres
- artifact storage: Supabase Storage
- queue strategy: `graphile-worker`
- PDF approach: HTML + Playwright
- architecture style: API-first, modular, microservice-ready, but not fully distributed microservices on day 1

### Market data

- use `yfinance` for the current build phase
- do not couple the system to `yfinance`
- keep a `MarketDataProvider` abstraction from day 1
- target provider for later production-grade swap may be Alpha Vantage or another licensed provider

### Narrative generation

- local/open-source LLM is acceptable for the dev build
- production provider decision is deferred
- keep a `NarrativeProvider` abstraction

### Report and compliance

- deterministic analytics remain source of truth
- AI narrative must only consume computed output
- disclaimer/compliance text must be system-owned, not generated by the LLM

### Data ownership and pricing readiness

- all portfolio and report records are user-linked
- `user_usage` is part of the schema
- usage must be trackable per user for future entitlement/pricing logic

### Portfolio and holdings model

- `portfolios.base_currency` is required
- MVP supported currencies are `USD` and `CAD`
- `report_runs.reporting_currency` is a frozen snapshot copy of portfolio base currency
- `portfolio_holdings` uses one consolidated row per ticker inside a portfolio
- duplicate ticker inputs should be aggregated in code before save
- DB still enforces uniqueness for `(portfolio_id, ticker)`

## 11a) Step 9 PDF Renderer

Step 9 is now implemented.

What was added:

- an HTML template builder (`src/server/renderers/build-report-html.ts`) that converts a validated `ReportDocument` into a self-contained HTML string
- a Playwright-based PDF renderer (`src/server/renderers/playwright-pdf-renderer.ts`) that implements the `PdfRenderer` interface

Important Step 9 design decisions locked during execution:

- the PDF uses a light/white professional report style, not the dark-themed landing page aesthetic
- web-safe system fonts are used: Georgia for headings, Helvetica/Arial for body, Courier New for numbers
- orange accent (#f96b2a) is used for headings and dividers to maintain brand connection
- the PDF has a dedicated cover page (page 1) with report title, portfolio name, date, currency, and branding
- content starts on page 2
- all CSS is inline — no external dependencies or font loading
- A4 print-optimized with 24mm top/bottom and 20mm left/right margins
- page-break controls are applied between sections
- the HTML builder is a pure function: `ReportDocument → string`
- all text content is HTML-escaped to prevent injection
- the executive summary is deterministically assembled from canonical snapshot totals and analysis summary fields — no LLM content
- the mandatory disclaimer is rendered from the system-owned `ReportCompliance` block
- section numbering is sequential: 01 (Executive Summary), 02-N (analysis sections in order), then Methodology, then Disclaimer
- the renderer writes PDF to `/tmp/secondact/{runId}/report.pdf`
- SHA-256 checksum is computed from the written PDF bytes and returned in the result
- the Playwright browser is always closed after rendering (including on failure)
- Step 9 produces a local PDF file only — Supabase Storage upload is deferred to Step 10

HTML template chapter order:

1. Cover page
2. Executive summary (totals, gainers/losers, HHI, key findings)
3. Analysis sections ×N (metrics grid → tables → findings → narrative block with takeaways → data quality flags)
4. Methodology & assumptions (all metadata, schema versions, methodology notes, data quality flags)
5. Important disclaimer (system-owned compliance text and version)

  - `ArtifactStorageService` class with constructor dependency injection following the established Repository + Service + DI pattern
  - `storeForReportRun(input)` method that: reads the local PDF, uploads to Supabase Storage at `{userId}/{runId}/report.pdf`, creates the `report_artifacts` metadata row with BigInt `fileSizeBytes`, then cleans up the temp directory

Important Step 10 design decisions locked during execution:

- storage path convention: `{userId}/{reportRunId}/report.pdf` under the `SUPABASE_REPORTS_BUCKET`
- the service validates both `userId` and `reportRunId` via `uuidSchema.parse()` before building the storage path (defense against path traversal)
- `fileSizeBytes` is stored as `BigInt` to match the Prisma schema definition
- when `renderResult.byteSize` is undefined, the service falls back to `fileBuffer.byteLength`
- when `renderResult.checksumSha256` is undefined, the service passes `null` to the database
- Supabase Storage upload uses `upsert: false` — re-uploading the same path is rejected. Duplicate uploads (orphaned blobs from prior attempts) throw `ArtifactAlreadyExistsError`, which the service catches and continues to the metadata write. Non-duplicate upload errors propagate normally.
- the temp directory containing the local PDF is cleaned up via `rm(tempDir, { recursive: true, force: true })` after successful upload
- the `StorageUploader` interface is thin and injectable so tests never hit real Supabase
- the Supabase admin client uses `{ auth: { persistSession: false } }` since it runs server-side only

Error classes:

- `ArtifactUploadError` — thrown when Supabase Storage upload fails
- `ArtifactMetadataError` — available for future repository-layer errors

### 12c) Vercel Deployment Fix — Dynamic Imports

Problem: Vercel `next build` failed during the "Collecting page data" phase. The 3 route files from Step 12b used top-level static imports of `report-run-service.ts`, which transitively imports `src/server/config/env.ts`. That module eagerly calls `parseServerEnv(process.env)` at evaluation time, and the 7 required server env vars are not available during the Vercel build step.

Root cause: `parseServerEnv()` in `env.ts` runs at module-evaluation time (not at request time), so any static import chain that reaches it will fail during build when env vars are not set.

Fix: Switched all 3 route handler files from top-level imports to dynamic `await import()` inside the handler functions:

- `src/app/api/v1/report-runs/route.ts` — `const { ReportRunService, PortfolioNotFoundError } = await import("@/server/services/report-run-service");`
- `src/app/api/v1/report-runs/[runId]/route.ts` — `const { ReportRunService, ReportRunNotFoundError } = await import("@/server/services/report-run-service");`
- `src/app/api/v1/report-runs/[runId]/pdf/route.ts` — `const { ReportRunService, ReportRunNotFoundError, ArtifactNotFoundError, SignedUrlError } = await import("@/server/services/report-run-service");`

Impact: Zero files from Steps 0–11 were touched. Runtime behavior is identical — same module, same classes, same error handling. The only difference is that module evaluation is deferred from build time to first request.

Verification: All 194 tests across 24 files pass. TypeScript and ESLint clean. This pattern is standard for Next.js App Router routes that depend on server-only env vars.

### 12d) Code Review Fixes — 3 Bug Fixes (Steps 9–12 Audit)

Three findings from a code review audit of Steps 9–12 were validated and fixed:

**Fix 1 (P1): portfolio.reportingCurrency sourced from baseCurrency instead of run.reportingCurrency**

- Root cause: `build-report-document.ts` line 167 used `canonicalSnapshot.baseCurrency` for the `portfolio.reportingCurrency` field, but this should be the run's reporting currency. If a user generates a report in CAD on a USD-base portfolio, the PDF would label values with the wrong currency.
- Fix: Changed to `run.reportingCurrency` in `build-report-document.ts`. Also fixed the same bug in `contracts/fixtures.ts` where the fixture used `canonicalSnapshot.baseCurrency`.
- Regression test added: `build-report-document.test.ts` — "uses run.reportingCurrency for portfolio context, not baseCurrency" — sets `run.reportingCurrency = "CAD"` with `baseCurrency = "USD"` and verifies both `metadata.reportingCurrency` and `portfolio.reportingCurrency` are `"CAD"`.
- End-to-end regression test added: `build-report-html.test.ts` — "labels currency as the run reportingCurrency, not portfolio baseCurrency (end-to-end)" — assembles a `ReportDocument` via `buildReportDocument` with `reportingCurrency = "CAD"` and `baseCurrency = "USD"`, renders it to HTML via `buildReportHtml`, and verifies the rendered output uses `CAD` for all formatted currency values and never labels amounts with `USD`.

**Fix 2 (P1): Enqueue failure leaves orphaned QUEUED row**

- Root cause: `report-run-service.ts` `createAndEnqueue()` created the `report_runs` row before calling `jobEnqueuer.enqueue()`. If enqueue failed, the API returned 500 but a QUEUED row with no worker job remained in the database.
- Fix: Wrapped the enqueue call in a try/catch. On failure, attempts best-effort `repository.deleteReportRun(run.id)` inside a nested try/catch to remove the orphaned row, then always rethrows the original enqueue error. The delete failure is swallowed so the caller always sees the root cause. Added `deleteReportRun(runId)` to the `ReportRunRepository` interface and `PrismaReportRunRepository` implementation.
- Tests added: `report-run-service.test.ts` — "deletes the created run when enqueue fails" (verifies cleanup is called) and "preserves the enqueue error when cleanup delete also fails" (verifies original error is not masked by delete failure).

**Fix 3 (P2→HIGH-01): Upload succeeds but metadata write fails → unrecoverable orphaned blob**

- Root cause: `artifact-storage-service.ts` uploaded the PDF to Supabase with `upsert: false`, then wrote the `report_artifacts` row. If the metadata write failed, the uploaded blob had no DB record, and retries would fail because the object already existed.
- Initial fix: Changed `upsert: false` to `upsert: true`. A security audit (HIGH-01) flagged this as a regression — `upsert: false` is the intended security control preventing unauthorized overwrites.
- Final fix: Reverted to `upsert: false`. Added `ArtifactAlreadyExistsError` subclass (extends `ArtifactUploadError`). `SupabaseStorageUploader.upload()` now detects duplicate errors ("already exists" / "duplicate" in the error message) and throws `ArtifactAlreadyExistsError`. `storeForReportRun()` wraps the upload call in a try/catch — catches only `ArtifactAlreadyExistsError` (orphaned blob from a prior attempt, safe to continue to metadata write), rethrows any other upload error.
- Tests updated: `artifact-storage-service.test.ts` — "allows retry after metadata write failure by tolerating duplicate upload" (simulates `ArtifactAlreadyExistsError` on retry, verifies service continues to metadata write) + "propagates non-duplicate upload errors without catching them" (verifies genuine `ArtifactUploadError` is not swallowed).
